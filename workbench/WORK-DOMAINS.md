# 工作包、SOP 与执行的职责

工作包描述一次工作的需求和材料。SOP 描述一种可复用的执行过程。一次执行把两者关联起来：同一包可以比较两版 SOP，同一版 SOP 可以处理多份包。`workspace` 是存放材料的位置，不是另一种业务对象。

## 独立完成条件

| 谁在办什么 | 完成条件 | 如何独立验证 |
| --- | --- | --- |
| 经办人准备工作包 | 需求已保存，该类型的必需材料已收齐。即使从未执行，这也是一份准备好的包 | 新建包时只提交类型和需求；分次上传材料，传错的材料在冻结前可以撤回重传；刷新后仍能查到 |
| 过程维护者发布 SOP | 执行器支持该配置，并产生一版可按标识和修订号读取的定义 | 不创建任何工作包，发布两版不同回执标题的 Echo SOP；两版均能独立查阅 |
| 经办人执行 | 本次尝试关联确定的工作包和 SOP 修订，有成功或失败记录 | 在同一包上运行两个版本，比较回执；找不到指定修订时不冻结包，也不假装已经尝试 |
| 经办人取结果 | 能从具体尝试读取本次产物或失败原因 | 不重新执行就能打开和下载旧回执；重启后仍能读取。回执不代表业务上已经通过验收 |
| 经办人派工、验收 | 通过派工模板创建工作项，交付的某一版由验收人通过或退回 | 在原派工路径分别提交两版交付，保留各版意见。单纯收取 Echo 回执不产生此类交付记录 |

## 决定放在哪里

- **类型**规定准备清单，首版内置「单条线索报告」的 Finding 和源码包两个材料角色。类型可以给执行入口推荐一个 SOP 版本；发布新修订不自动替换这个推荐。
- **包**保存本次需求与材料，不要求作者填写流程，不依赖 SOP 目录可用才能准备。准备就绪和已冻结是不同概念：前者描述材料齐全，后者表示已有执行使用这些输入。
- **SOP**在自己的目录管理。作者选择受支持的执行器，编辑与它对应的配置；Echo 的文本字段是回执标题。发布后修改配置产生新修订。
- **尝试**拥有实际采用的 SOP 和结果，执行请求无效与执行失败要能区分。再次执行不覆盖原尝试，也不重新派工。

## 工作台其余领域

资源库和具名执行器目录供派工模板引用，各自负责发布、指定版本读取和停用。外部来源负责从源条目派工，不签署执行结论。Flow 包负责流程定义，运行记录负责观测 Flow 运行。手动工作包目前只接入 Echo；界面不把尚未接入的 Agent、Flow 或资源列为可用能力。

界面中的「派工模板」是可复用的派工定义，协议集合仍为 `/api/v2/packages`；其中的办理说明是给经办人与 Agent 的文字，与可执行 SOP 分开管理。此次调整不将两条业务线的历史记录相互转换。
