# 执行器概念与结构

## 结论

在本项目中，**执行器（Executor）是一个可复用、可发布、可固定版本的通用执行能力**。它接受平台提供的一个 `workspace` 和一条 `workInstruction`，完成一次工作，并输出一个独立的 `artifactDirectory`。

```text
workspace + workInstruction
          ↓
       Executor
          ↓
   artifactDirectory
```

执行器定义回答“用什么能力完成工作”，执行尝试记录“一次实际运行发生了什么”，工作项记录“这次业务工作如何办理和验收”。执行器过程日志进入执行详情页，平台记录日志位于页面前部，执行器记录日志位于其后。两类日志的渲染查看逻辑暂留接口位置，后续再实现。

## 对象边界

### 派工模板

派工模板（`/api/v2/packages`）定义一类工作的目标、办理说明、动作和验收标准。每个动作绑定一个固定版本的执行器。

派工模板负责把业务要求组织成一次可执行的 `workInstruction`，并规定需要关注的输入材料和验收标准。它不保存某次执行的运行日志或制品目录。

### Work Patch 工作包

Work Patch（`/work-patches`）保存本次工作的文件目录。执行开始时，平台把工作包目录作为本次执行可访问的 `workspace` 输入，具体采用挂载、复制或受控映射由运行环境决定。

Work Patch 是业务材料目录，不是执行器的配置，也不是执行器的运行目录。执行器不直接获得主机路径，只获得平台分配的 workspace 能力引用。

### 配置包

配置包（`/config-patches`）保存可复用的 `AGENTS.md`、Skills 和 MCP 配置文件。它与执行器分别维护。

配置包参与执行时，需要由派工模板定义独立的配置包版本引用，并在创建工作项或启动尝试时冻结。配置包不能借用 `resources` 字段表达，也不能通过执行器自行读取配置包目录。

### 执行器

执行器是版本化的执行定义，声明：

- 执行后端类型和适用的环境策略。
- 接收 workspace 与 workInstruction 的方式。
- 资源依赖及其固定版本。
- 过程事件和结果的记录能力。
- 输出 artifactDirectory 的规则和能力。
- 可选的后端运行标识或过程日志引用能力。

执行器定义本身不持有某个工作包目录、某个制品目录、某个执行会话或某次日志。

### 执行尝试

执行尝试（`Attempt`）是一次真实运行的持久化记录。每次重试都产生新的尝试、workspace 能力和 artifactDirectory，旧记录保持不变。

尝试关联：

- 工作项和派工模板版本。
- 执行器 `id` 与 `revision`。
- 冻结后的 workspace 引用。
- 冻结后的 workInstruction。
- 独占的 artifactDirectory 引用。
- 平台记录日志和执行器记录日志。
- 实际环境、后端运行标识和最终状态。

### 执行详情

执行详情是一次尝试的稳定查看入口，页面名称使用「执行详情」。它是平台侧的统一入口，不要求每个执行器自己实现页面。

建议路径：

```text
/items/:itemId/attempts/:attemptId
```

页面按以下顺序组织：

1. **平台记录日志**：平台接收请求、准备 workspace、冻结工作指令、授权、启动后端、状态变化、取消、恢复、收集制品和错误。
2. **执行器记录日志**：执行器产生的标准输出、错误输出、阶段事件、Flow 节点摘要或后端事件。当前只保留展示位置和数据引用，渲染组件暂留空实现。
3. **制品目录**：展示本次执行返回的 artifactDirectory 引用和文件清单。目录查看和文件预览可以后续接入。
4. **后端详情入口**：存在固定 Flow Run、沙箱会话或执行器自定义查看页时显示跳转；没有时不显示空链接。

工作包列表中的「执行详情」按钮引用最近一次或指定的一次尝试。没有执行记录时保持不可用；存在尝试后链接必须带 `itemId` 和 `attemptId`，不能链接到执行器最新版本或当前运行状态。

## 通用执行契约

### 输入

平台向执行器提供两个固定输入：

```ts
type ExecutorInput = {
  workspace: WorkspaceRef
  workInstruction: WorkInstruction
}
```

#### workspace

`workspace` 是平台为本次尝试分配的、受访问控制的目录能力。它可以包含 Work Patch 中的工作材料，也可以包含平台按工作项快照准备的辅助文件。

```json
{
  "id": "workspace-attempt-42",
  "access": "read-write",
  "purpose": "work-input"
}
```

`id` 是平台标识，不是主机路径。执行器只能通过适配器获得目录操作能力，不能接收宿主机绝对路径、任意目录或其他工作项的 workspace。

workspace 的创建、隔离、挂载、回收和重启恢复由平台及运行环境负责。执行器可以在 workspace 中产生临时文件，但最终结果必须写入 artifactDirectory。

#### workInstruction

`workInstruction` 是启动时冻结的 UTF-8 工作指令。它由派工模板、工作项输入、动作说明和平台授权范围组合生成，作为一次调用的完整指令传给执行器。

```json
{
  "text": "检查 workspace 中的材料，生成可核查的排查报告。",
  "encoding": "utf-8"
}
```

第一版将它定义为文本，平台可以在文本中包含结构化约束、输出要求、材料说明和验收相关提示。执行器不读取派工模板或资源的当前版本来重新拼装指令。需要机器可读字段时，后续可以在 workInstruction 外增加稳定的元数据，而不改变 workspace 与 artifactDirectory 的主契约。

### 输出

执行器完成后向平台返回一个结果描述，其中制品位置是核心输出：

```ts
type ExecutorOutput = {
  artifactDirectory: ArtifactDirectoryRef
  status: "succeeded" | "failed" | "cancelled" | "unverified"
  summary?: string
  backendRunRef?: string
}
```

```json
{
  "artifactDirectory": {
    "id": "artifacts-attempt-42",
    "state": "frozen"
  },
  "status": "succeeded",
  "summary": "已生成排查报告和证据清单",
  "backendRunRef": "run-42"
}
```

`summary` 是执行摘要，不替代制品文件。执行器不返回一个代表全部结果的 `output` 字符串作为唯一产物。

### artifactDirectory

`artifactDirectory` 是平台为单次尝试分配的独立制品目录。执行器将最终生成的报告、证据、结构化数据或其他文件写入该目录，平台保存目录引用和文件元数据。

- 每次尝试拥有独立目录，重试不会覆盖历史制品。
- 执行中目录可写，终态后目录冻结为只读。
- 成功、失败、取消和待核实的尝试都保留目录；部分制品需要标注为未完成或未核实。
- 平台校验目录边界、文件名、符号链接、大小和可读性，不接受目录外路径。
- artifactDirectory 是执行结果，业务交付仍需由工作项模块选择文件、生成交付版本并提交验收。

## 日志模型

### 平台记录日志

平台日志由 Workbench 产生，记录执行生命周期和平台责任范围。每条记录至少包含事件时间、事件类型和安全的摘要：

```json
{
  "sequence": 12,
  "occurredAt": "2026-11-19T10:20:30Z",
  "source": "platform",
  "event": "artifact_directory_frozen",
  "message": "制品目录已冻结",
  "attemptStatus": "succeeded"
}
```

平台日志包括：

- 尝试创建、请求校验和版本绑定。
- workspace 分配、权限确认和清理。
- workInstruction 冻结和发送。
- 执行器启动、停止、重启恢复和状态变化。
- artifactDirectory 创建、收集、校验和冻结。
- 失败原因、待核实原因和人工核实记录。

平台日志不记录主机绝对路径、访问凭据或未经脱敏的底层异常。

### 执行器记录日志

执行器日志由执行后端产生，平台按序保存其事件或引用。日志载荷由执行器类型决定，可以包括：

- 标准输出和错误输出。
- 阶段开始、阶段完成和阶段失败。
- Flow 节点状态摘要。
- Agent 会话事件摘要。
- 后端提供的诊断信息。

平台保存来源、时间顺序、大小限制和关联的 attemptId。平台不把执行器日志解释为业务验收结论，也不把平台恢复提示覆盖成执行器日志。

当前阶段只定义两类日志的数据位置和页面顺序，查看器保持空实现。执行器日志的格式化、筛选、实时刷新和大文件加载另行设计。

## 执行器自定义日志页面

平台统一的执行详情是所有执行器都具备的入口。未来可以允许某些执行器提供自己的静态日志查看页面：

```text
平台执行详情
  └── 执行器日志页面（可选跳转）
```

扩展方向如下：

- 执行器版本声明一个受平台约束的静态查看页面入口。
- 平台按 `itemId`、`attemptId`、执行器版本和受控资源根生成跳转地址。
- 执行器页面只读取当前尝试的日志和制品，不读取其他尝试或宿主文件。
- 平台保留统一的「平台记录日志」和尝试摘要，不把自定义页面作为唯一审计入口。
- 自定义页面加载失败时，执行详情仍可查看平台日志和执行器日志原始引用。

静态路径嵌入、路径模板、资源托管、跨源策略和参数签名暂不固化为当前 API。当前页面只预留可选跳转位，不生成虚假的 URL。

## 执行器结构

### 公共定义

发布请求定义一个执行能力，服务端成功发布后生成 `revision`，最新版详情另带 `active`：

```json
{
  "id": "排查助手",
  "kind": "agent",
  "environment": "local",
  "resources": [
    { "id": "排查规范", "revision": 3 }
  ]
}
```

字段含义：

- `id` 是执行器对象标识，不是目录路径。
- `revision` 由服务端递增，发布请求不能指定。
- `active` 表示对象是否接受新引用、新派工和新版发布。
- `kind` 标识执行后端类型。
- `environment` 是环境选择策略，`local` 使用服务端配置的本地执行环境，`sandbox` 使用管理员预配的独占沙箱。
- `resources` 是可选的固定版本资源引用，当前用于 Skill 和提示词。
- 平台为每次尝试统一保存平台记录日志、执行器记录日志和独立的 artifactDirectory；这些是尝试侧输出，不是执行器定义字段。

执行器定义不保存 workspace、workInstruction、artifactDirectory、attemptId、日志正文或运行中的会话。

### Agent

Agent 执行器使用管理员配置的 Agent 程序，把 workspace 和 workInstruction 交给一次受控调用，并把生成的文件写入 artifactDirectory。

```json
{
  "id": "排查助手",
  "kind": "agent",
  "environment": "local",
  "resources": [
    { "id": "排查规范", "revision": 3 },
    { "id": "报告格式", "revision": 1 }
  ]
}
```

程序路径、命令行、模型、密钥、主机目录和并发限制由部署配置管理。浏览器只配置执行器类型、环境策略和固定资源引用。平台统一提供执行日志与制品目录管道。

### Agent Flow

Agent Flow 执行器引用固定的 Flow ID 和目录修订，由 Flow Runtime 接收 workspace 与 workInstruction，并将 Flow 产物收集到 artifactDirectory。

```json
{
  "id": "复现验证",
  "kind": "flow",
  "flowId": "reproduce-fix",
  "flowRevision": "2026-11-19.1"
}
```

Flow 执行器不能通过 `environment` 选择 Agent 环境，也不把 Flow 的最新目录当作固定修订。Flow 节点历史由 Runtime 产生，Workbench 保存关联引用并在执行详情中提供后端入口。

## 版本、绑定与冻结

执行器的生命周期如下：

1. 在 `/executors/new` 填写一个新执行器定义。
2. 服务端校验执行器类型、后端绑定和资源引用。
3. 发布成功后生成不可变的 `revision`。
4. 派工模板发布时，动作绑定一个已启用执行器的固定 `{id, revision}`。
5. 发布派工模板时冻结执行器定义及资源依赖，并校验动作能生成所需的 `workInstruction`。
6. 创建工作项时保存派工模板版本和 Work Patch 目录引用。
7. 启动尝试时创建独立 workspace、冻结 workInstruction、分配 artifactDirectory，并写入平台日志。
8. 执行器完成后，平台收集和校验 artifactDirectory，追加执行器日志和平台日志，最后冻结制品目录。
9. 停用执行器对象后禁止新引用、新版发布和新派工，已发布版本、历史尝试和历史制品继续可读。

重试创建新的 workspace、artifactDirectory 和日志序列。任何新版本的执行器、派工模板或资源都不改变已经启动的尝试。

## 业务交付与验收

artifactDirectory 是执行产物集合，交付是业务模块对产物的选择和提交。两者按以下顺序衔接：

1. 执行器向 artifactDirectory 写入结果。
2. 平台冻结目录并提供清单。
3. 经办人从目录选择文件，生成工作项交付版本。
4. 工作项保存交付文件快照、来源 attemptId 和验收记录。
5. 验收通过只改变业务交付状态，不改变执行器日志和历史制品。

执行成功、制品目录冻结、交付提交和验收通过是四个独立状态。失败或待核实执行的部分制品可以用于诊断，不能自动成为已验收交付。

## 与现有实现的关系

当前仓库已按本文件完成了第一个迁移切片：`workspace + workInstruction → artifactDirectory` 的尝试侧契约，以及执行详情的三区域基础结构。其余部分仍是迁移前形态。

### 已实现（迁移切片）

- 执行尝试记录 `workspace` 引用、冻结的 `workInstruction`、独占的 `artifactDirectory` 引用、平台记录日志、执行器记录日志和可选 `executorLogPage`。旧 `output` 字段保留，与制品目录并存。
- 平台向本地 Agent 提供 `URSI_ARTIFACT_DIR` 制品目录能力；平台登记目录、提供清单并在尝试终态（含失败、取消、待核实）后冻结。当前内置 Pi 调用关闭工具和扩展，因此本切片只接通目录传递与收集管道，实际写入需要后续执行器能力或受控包装程序。重试使用新目录，历史制品不变。冻结目录拒绝写入、移动和删除，读取仍可用；工作包和配置包目录不冻结。
- 平台恢复提示与执行器 `output` 分开保存，重启、查询和人工核实都不会覆盖执行器输出。
- 执行详情（仍在工作项「执行记录」内展开）依次提供「平台记录日志」「执行器记录日志」「制品目录」，日志查看器留空，`executorLogPage` 为 `null` 时不渲染任何跳转。

### 未实现（当前边界）

- 派工模板仍以 `inputs`/`outputs` 端口声明字段，Agent 仍接收平台拼装的文本指令；当前内置 Pi 调用使用 `--no-tools` 等隔离参数，尚未让它直接写入制品目录；Flow 仍以工作项 `input` 作为变量。
- Flow 和沙箱当前只登记并冻结制品目录，尚未把后端产物收集到其中；交付接口仍接收文本文件对象，尚未从 artifactDirectory 选择文件、生成交付版本或冻结文件快照。
- 平台日志和执行器日志只保存数据与条数，尚未实现查看器、实时刷新、筛选、折叠、高亮和 Flow 节点图；执行器自建静态日志页的路径模板、资源托管和跨源策略尚未定义，也没有任何跳转地址。
- 执行器定义仍未声明日志页和制品规则字段。


## 页面结构建议

执行详情页面使用稳定的尝试深链：

```text
执行详情
├── 平台记录日志
├── 执行器记录日志
├── 制品目录
└── 后端详情 / 自定义日志页（可选）
```

页面首版先完成数据区域、链接关系和空状态。平台日志和执行器日志的具体查看器、实时刷新、过滤、折叠、文本高亮、Flow 节点图和执行器静态页面嵌入留待后续设计。
