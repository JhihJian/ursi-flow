# 工作清单与工作包来源

工作清单记录要做的事，工作包保存某一次工作用到的文件。经办人可以只记一条工作，也可以为它选择外部资源、编写 Python 转换脚本，并在需要时生成一个工作包。例如，「每周客户反馈」是一条持续工作，每周读取一次反馈服务的资源就得到一个独立的包。上周的包仍能打开，本周的包也归在同一工作项下。

## 工作清单怎么用

清单提供新建、查看、编辑和删除。新建只需标题，默认归入「待开始工作」，说明和工作包来源可留空。列表按类别筛选，每行显示标题、类别和关联工作包数。详情页分为工作说明、工作包来源、关联工作包三部分，包名链接到已有的[工作包编辑台](PATCH-STUDIO.md)。

| 类别 | 业务含义 |
| --- | --- |
| 待开始工作 | 已记录，尚未着手，例如下月的材料核查。 |
| 正在进行中工作 | 已着手、有明确结束点，例如本月的材料核查。 |
| 持续工作 | 长期保留、可反复办理，例如每周整理客户反馈。 |
| 已完成工作 | 经办人确认该事项结束，可继续查阅材料。 |

每项只属于一类，经办人可直接改类，也可重新打开已完成的工作。类别只决定清单归类。选择「持续工作」不会启动定时任务，生成或执行工作包也不会自动改变类别。

## 从资源到一个工作包

1. **平台登记 MCP 服务。** 管理员在平台设置中保存服务名称、稳定的 `serverId`、允许连接的地址和服务端凭据引用，登记时校验管理员的出站授权，查看资源时建立连接。平台通过 MCP `resources/list` 按游标列出资源，界面显示服务名、资源名和 URI。平台连接设置独立于 Flow，也独立于面向执行器的配置包 `mcp.json`。
2. **在工作项上定义来源。** 经办人从列表中勾选一个或多个具体资源，每个引用保存 `(serverId, uri)`，并为脚本指定唯一别名，如 `feedback`。同名资源可用服务名和 URI 区分。工作项保存一份可编辑的配方：有序资源引用和一段 Python 脚本。保存配方只改定义，不取材料、不建包。
3. **手动生成。** 经办人点击「生成工作包」。服务端固定本次工作项和配方修订，按权限通过对应 MCP 服务的 `resources/read` 获取内容。脚本收到本次读取的只读快照，同一次生成始终使用这批材料。服务停用、资源消失或读取失败时，指明失败的服务与资源，不以空内容代替。
4. **登记并打开包。** 转换器返回一个包名和一组文件。服务端校验后复用[包与目录分配逻辑](server/src/work/patches.rs)，一次登记文件目录、工作包及其归属。新包出现在工作项详情和工作包列表中，可以继续编辑。下次主动生成创建另一个包，不覆盖之前的文件。

### Python 的输入与输出

入口为 `transform(item, resources)`。`item` 是工作项的 ID、标题、说明和类别快照。`resources` 按别名索引，每项包含服务标识、URI，以及 MCP 读回的 `contents` 列表。文本保留 `text`，二进制保留 Base64 `blob`。返回值含 `name` 和 `files`，每个文件给出包内相对路径，以及 `text` 或 Base64 `blob` 二者之一。例如，反馈资源约定第一段内容是 Markdown 文本：

```python
def transform(item, resources):
    feedback = resources["feedback"]["contents"][0]["text"]
    return {
        "name": item["title"],
        "files": [{"path": "材料/反馈.md", "text": feedback}],
    }
```

平台负责访问外部系统和写入正式目录，脚本只处理输入快照并返回文件。脚本在无网络的隔离进程内存中运行，宿主工作目录、平台凭据和其他包对脚本不可见。平台强制执行时限、内存、文件数量和总字节上限。输出按[虚拟目录规则](server/src/work/directories/HTTP.md)校验全部路径，并拒绝重复路径、文件与目录冲突及非法编码。缺少隔离环境时禁用生成，工作项仍可正常增删改查。

## 当前归属与生成来源

**一个工作包当前关联零或一个工作项，一个工作项可以关联零到多个包。** 唯一的归属字段是文件型工作包 `workPatches.workItemId`，可空、非空时必须引用有效工作项。工作项详情按这个字段查询包。配置包和派工模板不参与该关系。

| 操作 | 结果 |
| --- | --- |
| 手动建包 | 可不选工作项。稍后可从包详情选择、改绑或清除归属。 |
| 从工作项生成 | 服务端把当前项设为归属。独立保存生成来源：生成时的项 ID 和标题、配方修订及脚本摘要、每个资源的服务标识、URI、内容摘要和读取时间。 |
| 修改配方、移动包或解绑 | 当前归属可变，生成记录保持原样。外部资源变化不会改写已生成的文件。 |
| 删除工作项 | 确认框显示受影响的包数。在一次存储更新中清空这些包的归属并删除工作项。包、文件和生成记录照常可读。 |

每次主动生成有独立请求标识。同一次点击因网络重试时返回同一个包，主动再次生成才创建新包。发布前再次检查工作项存在且配方修订一致；生成期间删除工作项或修改配方时返回冲突，清理暂存结果。脚本报错、超时或任一文件非法，整次生成失败，列表中不会出现空壳包。

## 与现有派工的边界

现有 [`/api/v2/items`](server/src/work/items/HTTP.md) 保存按模板版本派出的办理单，状态受交付与验收约束。新清单使用独立集合 `/api/v2/work-items`，不把待验收单自动归成已完成工作。导航将「工作清单」指向新页面 `/work-items`，原 `/items` 独立命名为「派工记录」。现有[文件来源](server/src/work/sources/README.md)从本地导出条目派单，仍走派工接口。新来源的产物是 `workPatches` 文件包，生成时不会派单或启动执行器。

## 验收场景

- 未配置 MCP 时，创建一条待开始工作，修改标题和类别，刷新后按新类别查到该项，再删除。全过程无需派工模板或执行环境。
- 配置两个 MCP 服务，各列出同名资源。选择其中一个资源，保存脚本并生成，核对文件只含所选服务的数据。更新外部数据后再生成，两个包分别保有两次的内容，均指向同一工作项。
- 模拟生成响应丢失，使用相同请求标识重试仍只有一个包。让资源读取失败、脚本超时、脚本返回越界路径，或在转换期间删除工作项，每次均不会新增包或可见目录。
- 手动建一个无归属包，把它关联到某项后再改绑。两个工作项的包列表随之更新。删除该项时保留所有包；从已删除工作项生成的包仍显示原始来源。
