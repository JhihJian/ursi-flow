# Server v2：从工作包到交付

**设计目标：管理工作包、可复用资源和执行器，按工作包发起工作项，并跟踪每项工作直到交付验收。** 平台的业务入口是工作清单。操作者可以看到正在办什么、还缺什么、下一步由谁处理，以及最后交付了什么。Agent 和 Agent Flow 提供执行能力，哪一种适用由工作包决定。v1 的 Flow 管理入口见 [Server v1 设计](DESIGN.md)。

**当前实现。** `/api/v2` 已提供定义发布和停用、工作项派工和办理、执行尝试、文本交付和验收。工作记录存于 Server 私有的 `work/`，与 Flow Runtime 数据分开。受信本地 Pi 和固定修订的 Flow 已接入；预配沙箱适配器的自动测试只覆盖模拟 CLI 契约。可选来源只读管理员提供的 JSON 文件。配置及 API 入口见 [Server 使用说明](README.md)。

## 四类管理对象（目标模型）

| 对象 | 负责回答 | 管理内容 |
| --- | --- | --- |
| 工作包 `WorkPackage` | 这类工作怎样才算办好？ | 目标、输入材料、SOP、专用资源或共享资源引用、可用动作及其执行器、交付物要求与验收标准。支持编辑草稿、校验、发布和停用。 |
| 可复用资源 `Resource` | 办理工作可以用什么？ | 维护 Skill、提示词和 MCP 工具配置，供多个包或执行器按版本引用。MCP 配置声明连接方式和所需授权，只保存凭据引用。 |
| 执行器 `Executor` | 把这一步交给什么工具执行？ | 独立登记、配置、发布和停用具名执行器，例如“排查助手”（Agent）和“复现验证”（Agent Flow）。每版声明输入、输出、资源依赖、所需环境能力及对应的运行后端。 |
| 工作项 `WorkItem` | 这一次办到哪里了？ | 保存工作包版本、来源、当次输入、经办信息、业务状态、每次执行、历次交付和验收意见。支持从内置清单发起、按状态查找和继续办理。 |

SOP 可以只是一份供人和 Agent 遵循的步骤说明。要自动选择分支、循环或编排多个节点时，工作包的动作绑定一个 Agent Flow，由 Flow Runtime 解释其 `FLOW.md`。沙箱描述执行地点：同一个 Agent 可以在不同的获准环境中运行，前提是后端支持该组合。

### 定义怎样变成一次工作

工作包发布时固定 SOP、验收标准和资源版本，并将每个动作绑定到一个已发布的执行器版本。执行器本身可以被多个工作包复用。发布前解析包括执行器依赖在内的资源，缺失引用、同名绑定冲突或输入输出不匹配均拒绝发布，旧版仍可使用。停用阻止新引用或新派工，历史版本继续可读。因安全原因撤销的工具授权则在每次执行时重新检查，旧工作项也无权绕过。

工作项创建时选择一个已发布的包版本，记录实际输入。每次执行另建 `Attempt`，绑定工作项、动作、执行器版本、实际资源和环境、后端运行标识与结果。返工新增执行记录，不覆盖旧记录。提交交付时生成一版 `Delivery`，包含可打开的成果、来源执行和验收记录。一次工作可有多次执行，一次交付也可汇集多次执行的成果。

## 一项工单怎样办完（目标场景）

当前入口是 HTTP 工作清单；定制页面、继续对话和自动收取远端文件属于扩展目标。以“客户工单排查”包为例。它有两个固定动作：“分析原因”使用对话 Agent，读取工单材料和日志分析 Skill；“验证修复”使用 Agent Flow。验收标准是提供可核查的原因说明和复现结果。

1. **发起。** 操作者从内置清单选包、填写工单编号及材料，生成工作项。安装外部工单扩展后，也可以从定制列表点击同一动作，得到同样可在内置清单查到的工作项。
2. **办理。** 经办人执行“分析原因”，在工作项上看输出、补材料或继续对话；需要复现时再执行“验证修复”。后台分别记录两次执行，Flow 的节点仍归 Flow Runtime 管理。一次失败可以在原工作项显式重试。
3. **交付。** 经办人把原因说明和验证报告提交为一版交付物。Server 将文件收存至工作项的持久存储，校验可读后转为待验收。关闭终端、退出 Agent 或回收沙箱均不影响报告读取。
4. **验收。** 验收人按该包版本的标准通过或说明退回原因。退回后仍在同一工作项上补材料、执行和重新交付，两版报告及意见分别可查。

| 工作项状态 | 进入条件 | 下一步 |
| --- | --- | --- |
| 待办理 | 已发起并保存包版本与输入 | 经办人开始办理 |
| 办理中 | 已开始，或交付被退回 | 补材料、调用执行器、提交交付 |
| 待验收 | 本次所需交付物已收存 | 验收人通过或退回 |
| 已交付 | 验收通过，记录所通过的交付版本 | 查阅成果与历史 |

执行的进行中、成功、失败、取消、待核实属于 `Attempt`。停止一次执行只影响这次尝试。工具返回成功不会自动转换工作项状态，退回也不会自动重新执行有副作用的操作。首版按现有可信操作者部署，经办和验收是业务动作，可由同一操作者完成；独立身份与职责分离需要另外的认证能力。

## Server 与扩展的分工

Server 保存上述四类对象、执行关联和交付记录。工作管理层通过执行适配器发起、查询和取消执行，适配器报告支持的能力及完成证据。Server 展示业务摘要和后端详情入口；Flow 节点历史、Agent 会话事件和沙箱资源状态分别向其所有者查询。首版采用单个 Server 进程和显式装配的适配器，无需可动态加载的插件系统。

在 `server` 内，定义管理、工作项办理和后端适配分别负责发布、业务状态变更和外部调用。HTTP 层只解析请求、鉴权并调用这些用例。`app` 按部署配置装配适配器，只有启用本机 Flow 时才管理 `ursi-flowd`。运行后端不得直接修改工作项或签署验收结论。

| 扩展接口（设计目标） | 提供什么 | 接入边界 |
| --- | --- | --- |
| 执行适配器 | Agent 对话执行、Agent Flow 执行 | 两者均接收已解析的任务和资源，返回后端标识与结果。继续对话、流式事件、结构化结果按能力暴露。模型的一轮回复只结束当前调用。 |
| 环境提供方 | 分配和释放受信本地工作区或沙箱，公布可用通道 | 部署者授权环境。沙箱 Gateway 管资源，Runtime 管会话，Server 保存关联和收存成果。指定隔离执行的工作，在沙箱不可用时不得回退至宿主机。 |
| 观测与操作通道 | PTY、浏览器、文件列表、预览与管理 | 通道绑定工作项本次执行及获准工作区。终端输出与输入、浏览器查看与控制、文件读与写分别授权。只展示实际提供的能力。新增浏览器通道不改变工作项模型。 |
| 外部资源平台连接器 | 按平台列出资源、读取单项材料、公布固定动作 | Web 提供定制列表。页面传来源、资源 ID 和动作 ID；Server 重新校验资源访问权和动作权限，用预设工作包及绑定执行器派工。源平台拥有工单原文，工作项保留来源标识和办理时使用的必要材料。 |

未配置来源或沙箱时，受信本地执行器也能完成从派工到验收的全程。`URSI_FLOW_ENABLED=0` 时不启动 daemon，Agent 型工作包可独立工作，Flow 动作不可执行。密钥只在获准后端调用时解析，不进入包版本、执行摘要、日志或交付物清单。

## 当前实现与接入边界

- **Flow 固定修订（pinned）已实现。** 工作项以尝试 ID 为运行 ID，通过 [FlowClient::start_pinned](../../flow-runtime/client/src/lib.rs) 在一次 `run.startPinned` 请求中提交 `flowId` 与 `flowRevision`。daemon 在受理启动时核对[整个 Flow 目录的修订](../../flow-runtime/src/machine/catalog.ts)，执行核对过的快照。修订不匹配返回 409，保留失败尝试，不创建运行或执行节点，也不回退到普通启动。CLI 可按同一 ID 查询成功启动的运行及节点历史。
- **沙箱会话。** Server 通过 CLI 连接管理员为单个工作项预配的独占 ACP 沙箱，保存会话 ID 后才发送 prompt，可查询收尾证据、取消或人工核实。未配置或绑定不符时不回退本地。Server 不负责经 Gateway 创建或回收环境，也没有 SSH/SFTP、PTY、浏览器或通用文件管理入口。文件 API 读取的是已提交的交付文本。MCP 资源可登记引用，当前执行器不支持注入。
- **来源。** `json-file` 按管理员配置的本地 JSON 导出列出资源、读取单项材料并按固定动作派工。平台 SDK、平台侧鉴权和定制 Web 列表仍是设计目标。
- **断线与重复提交。** 派工操作接受请求标识，同一标识和参数返回原工作项，参数不同则冲突。执行前先持久化尝试标识，Flow 以此为运行 ID，沙箱在发送 prompt 前记下会话标识。响应丢失后优先查询；缺少完成证据则标为待核实并提示可能已有副作用，不自动重发 prompt。操作者核实后显式重试会产生新的尝试。

## 验收范围

1. **本地 Agent 与交付。** [工作管理 HTTP 验收](tests/WORK-ACCEPTANCE.md) 在关闭 Flow 的部署中用同一包办理两单，一单通过，一单退回，重启后核对各单的交付文本和状态。该阶段调用真实 Pi CLI，模型端点返回固定的模拟报告，验证的是固定版本材料传递和办理流程。
2. **固定修订 Flow。** 同一验收的 Flow 阶段使用真实 daemon、命令节点和独立 CLI。两个包共用一个执行器，先核对一单的节点输出和历史；更新 Flow 目录后，另一张旧单按原修订启动返回冲突，未产生新的运行或命令副作用。
3. **文件来源与预配沙箱。** 重复提交相同的文件来源派工只产生一个工作项。沙箱自动测试用模拟 CLI 检查会话绑定、断线不重发及取消收尾，仅作契约验证。真实独占沙箱的执行、取消与关闭需按[真实会话验收步骤](src/work/execute/SANDBOX.md)单独验证。
4. **扩展验收目标。** 平台定制列表须验证重复派工只建一单；只读通道须拒绝写文件、控制浏览器和终端输入；远端成果须在沙箱回收前收存，回收后仍可验收。这些场景随相应扩展另行验证。
