# 位置契约

位置契约把「哪台机器的哪个目录」统一成一个 URI：`file:///abs/path` 表示工作台所在机器，`ssh://<设备名>/abs/path` 表示远程设备，设备名就是 ssh-web 里的连接名。它是一组纯函数加一份共享测试向量，没有进程也没有数据库，各模块照旧独立部署。功能与验收以 [packages/location/SPEC.md](../../../packages/location/SPEC.md) 为准，这里记录决策的来龙去脉：问题是什么、基座是什么、为什么是 URI、设备清单归谁、怎么落地、明确不做什么。

## 问题

这个工作台是单人自托管的，用途是安全审计、开发和运维，由多个可以独立部署的 Web 应用组成。
用户真正的工作单元是「哪台机器的哪个目录」，但这个事实过去在 [fs-web](../../../apps/fs-web/README.md)、[ssh-web](../../../apps/ssh-web/SPEC.md)、[pi-web](../../../apps/pi-web/SPEC.md)、[todo-web](../../../apps/todo-web/SPEC.md) 和 [flow-web](../../../apps/flow-web/SPEC.md) 里各存一份，形式还不一样：有的存裸路径，有的存 realpath 的哈希，有的存一个 cwd 字符串。

形式不一带来的后果是一条一条具体的断点：

- fs-web 添加目录时没有地方填「在哪台机器上」，远程目录无处可填。
- 选目录器只知道本机，因为它的入参是本机路径，没有设备这个维度。
- todo-web 与 flow-web 打开项目目录时只能指向本机，项目如果在远程设备上就打不开。
- 想把「在某目录开终端」接起来时，发送方和接收方没有共同的词可以指代那个目录。

这些断点的共同原因只有一个：缺一个跨模块共用的说法。
每个模块单独看都合理，fs-web 的哈希是为了得到跨重启稳定的 id，pi-web 的 cwd 是为了启动子进程，ssh-web 的连接名是为了列在侧栏里。
问题出在它们要把目录交给别人的那一刻：各自的表示里都没有「机器」这个维度，或者有但别人不认。

## 基座是什么，不是什么

缺共同的说法，最直觉的做法是新建一个基座服务，带数据库，管项目、管设备，所有应用都向它注册。
这个方案被认真评估过，因为它看起来一次解决两个问题：既有共同的说法，又有统一的项目与设备管理。

评估下来它被否掉，理由是成本与收益不对等。
成本这一侧，单人工具多一个有状态的进程，就多一个要备份、要迁移、要排障的东西，部署上多一个必须先起来的依赖，任何一个应用要访问目录都得先问它一次。
收益这一侧，要解决的问题只是各模块之间缺一个共同的说法，并不需要任何一方替别人保管事实：设备清单已经由 ssh-web 的连接表保管，目录清单已经由 fs-web 的状态文件保管，pi 的 home 清单已经由 pi-web 保管，再集中一份只是复制，而且复制出来的那份迟早会和原件不一致。

基座服务一旦存在，各模块就会倾向于把它当成公共数据库，把本该自己管的事实放进去，模块边界会慢慢失效。
这与仓库里「模块之间不互相 import，跨模块协作走组合根」的约定是相反的方向。

所以基座的定义收窄为一句话：基座是契约与约定，不是一个服务。
它落在 [packages/location](../../../packages/location/package.json) 这个包里，只有解析、构造、派生、规范化和求键的纯函数，前后端都能引用。
没有基座数据库，没有基座进程，模块之间不互相 import，跨模块协作照 [MODULE-CONTRACT.md](../../../packages/workspace-shell/MODULE-CONTRACT.md) 第 8 节的组合根注入走。
契约要做的只有一件事：让「哪台机器的哪个目录」有一个所有模块都认的写法。

## 为什么是 URI，为什么是这个形态

### 三种方案的比较

让「机器加目录」跨接口传递，一共有三种形态可选。

第一种是结构化对象，每个接口里展开成 `host` 与 `path` 两个字段。
它的缺点是字段要成对出现在所有地方：接口签名里是两个参数，日志里是两列，配置文件里是两个键。
任何一处漏掉 `host` 就退回到「默认本机」的隐式语义，而这正是要摆脱的局面。
它也没有一个可以整体比较的值，判断「是不是同一个目录」要两个字段都比一次。

第二种是继续用裸路径，靠「当前设备」这个上下文隐式表达机器。
这正是问题的来源：上下文在模块之间传递时会丢。
选目录器和 todo-web 之所以只知道本机，就是因为它们拿到的裸路径不带设备，它们只能假设本机。
要在每个接口上补一个「当前设备」参数，就回到了第一种方案的字段成对问题，而且更容易漏。

第三种是 URI 字符串，也就是最终选定的方案。

选它的理由有两条。
其一，一个字符串就是一个完整的身份，机器和目录都在里面，可以放进任何接口、日志、剪贴板和配置文件，不需要额外携带上下文。
判断两个位置是否相同就是比较两个字符串，发到终端里就是一个 cwd。
其二，它与 git、GVfs、sshfs 这些跨机器文件工具的惯用形态一致，用户见到 `ssh://nm105/srv/proj` 不需要学习，在终端里敲 `ssh nm105` 再 `cd /srv/proj` 得到的就是同一个地方。

本机位置写成 `file:///abs/path`，并且接受裸绝对路径与 `~` 作为简写。
保留简写是因为在命令行与配置文件里写 `/data/dev/x` 是肌肉记忆，强迫用户写完整的 `file://` 只会制造无谓的报错。
简写只在入口处被接受，解析之后一律以 URI 为唯一事实源。

### 形态上的五条取舍

形态借 RFC 3986 的样子，具体规则有五条，每条都对应一个被放弃的做法。

**借 RFC 3986 的形，但不经 URL 解析器。**
身份层必须原样保留设备名的大小写，这一点有实证：在本机执行 `ssh -G nm105` 得到 `HostName 172.16.126.105`、`Port 10000`，而执行 `ssh -G NM105` 得到 `HostName NM105`、`Port 22`。
OpenSSH 的 Host 别名大小写敏感，`NM105` 与 `nm105` 是两台不同的机器，后者根本解析不到真实地址。
身份层不能把它们折叠成一个，否则用户输入时打错一个字母就会被静默指向另一台机器。
交给通用解析器还有另外两个不可控的地方：未编码的 `#` 会被当成片段截掉，`%2F` 不会按段还原成一个普通的文件名。
所以 [index.ts](../../../packages/location/src/index.ts) 自己按 `://` 切 scheme，路径按段做 percent-encoding，文件名里的空格、中文、`#`、`%` 全部可逆。
不让通用解析器插手，是因为身份层的规则要比通用规则窄，窄的部分必须由契约自己说了算，不能依赖某个运行时的解析器恰好怎么处理非特殊 scheme。

**设备名只是连接名，不收 `user@`，不收 `:port`。**
设备名只允许 `[A-Za-z0-9][A-Za-z0-9._-]*`。
用户、端口、跳板机、密钥这些连接参数全部归 ssh-web 的连接命令表达，位置只回答「哪台」。
把用户名写进 URI 的做法被放弃，因为同一个设备换个用户登录不该变成另一个位置，而连接参数本来就有唯一的事实源，写两份就会不一致。
位置里一旦带了用户与端口，ssh-web 改了连接命令之后所有指向它的 URI 都会失效，身份层就不再稳定了。

**不折叠 `..`，不做 Unicode 归一化。**
身份层只做词法规范化，具体是三件事：以 `/` 开头、折叠连续斜杠、去掉尾斜杠。
越界防护交给各 provider 的 realpath，fs-web 的本机与 ssh provider 都是先 realpath 再做前缀校验。
不把 `..` 的折叠放进身份层，是因为「这个路径实际指向哪里」只有文件系统能回答。
设 `a/link` 是指向 `b/c` 的符号链接，用户写的 `a/link/../x` 由内核解析为 `b/x`，而词法折叠会把它改成 `a/x`，指向的是另一个目录。
身份层一旦替文件系统做了这次折叠，用户给的位置就悄悄变了。
两层各管一件事：身份层保证同一个写法得到同一个身份，provider 层用 realpath 求出实际落点并保证访问不越界。
同理不做 NFC 与 NFD 的归一化，文件系统给什么就是什么，归一化只会在非 ASCII 文件名上制造出看似相同实则不同的两个身份，或者反过来把两个真实不同的文件判成一个。

**URI 是身份，不是存储键。**
存储键是 [keys.ts](../../../packages/location/src/keys.ts) 里的 `keyOf`，取规范 URI 的 sha256 前 16 位 hex。
这个算法与 fs-web、pi-web 既有的 realpath 哈希一致，不引入新算法，跨进程、跨重启稳定。
`keyOf` 放在 `@ursi/location/keys` 子出口而不是主出口，因为它依赖 `node:crypto`，而主出口要被选目录器这类浏览器代码直接引用，必须保持纯浏览器可用，有测试守着主出口不出现任何 `node:` 模块。
身份与键分开，是因为两者的用途不同：URI 给人看、给人抄，要能一眼读出是哪台机器的哪个目录。
键给程序用，要定长、要能当文件名、要能放进 URL 的一整段里，这两组要求放在同一个值里满足不了。

**URI 不是 HTTP 传输层。**
fs-web 的文件接口继续用 `workspaceId + segments[]`，进入传输层后 URI 退场。
原因是文件名里的 `#`、空格、中文放进 URL 都要二次编码，一次编错就是 404 或者打开错文件，而 JSON 字段里的字符串数组没有这个问题，服务端拿到什么就是什么。
URI 只负责标清「哪台机器的哪个目录」，怎么传文件是另一件事。
把 URI 直接当成请求路径的做法被放弃，因为它把身份层的编码规则和传输层的编码规则搅在一起，任何一边变了都要重新验证另一边。

## 设备清单归谁

设备名就是 ssh-web 的连接名，所以 ssh-web 的连接表就是设备注册表，`~/.ssh/config` 只是导入源之一。
这个归属不是随意指定的：连接名是用户在 ssh-web 里亲手起的、全局唯一、已经能连上机器的名字，它天然就是「哪台」。
fs-web 不复制也不缓存这份清单，需要时现问。
如果 fs-web 自己也维护一份设备表，两边迟早不一致，用户在 ssh-web 里改了名字，fs-web 里的远程目录就会集体失效。

ssh-web 为此新增了一个只读接口 `GET /connections/by-name/{name}/ssh-args`，按连接名返回这条连接的 ssh 调用参数，也就是连接命令去掉首词 `ssh` 与 `-t`、`-tt` 之后的部分，`-p`、`-i`、`-J` 与 config 别名原样保留。
fs-web 服务端的 ssh provider 从 URI 解出设备名后，用这个接口换取实际连机器的参数，再拼到 `ssh` 后面执行，地址由 `SSH_WEB_API` 注入。
这是仓库里第一条服务到服务的边，方向是 fs 到 ssh。
它不经过浏览器，也不经过组合根，因为调用发生在 fs-web 的服务端进程里，与前端怎么接线无关。
ssh-web 不可达或设备未登记时，错误被隔离在 ssh provider 内，分别返回 `ssh_unavailable` 与 `device_not_found`，本机目录不受影响。

fs-web 不建连接池。
用户的 ssh 配置里已经有 `ControlMaster auto` 与 `ControlPersist`，第一次连接之后 OpenSSH 自己会复用那条通道，一次操作一次 ssh 调用的开销只是一次本地进程启动加一次复用握手，可以接受。
连接池意味着 fs-web 要保管连接生命周期、处理断线重连、在服务退出时清理，这是另一个有状态的东西，和基座被否掉是同一个理由。

## 分四步落地

落地分成四步，每一步单独可用，前一步不依赖后一步。

1. **location 包。** 交付 `parse`、`build`、一组从一个位置推出相邻位置的派生函数、求持久化键的 `keyOf`，以及一份两边共用的 `vectors.json`。
   ssh-web 的 Rust 侧用 `include_str!` 读同一份向量文件，所以 TS 与 Rust 对同一个 URI 的理解从第一天起就是对齐的，不靠人肉对照。
   这一步先做，因为后面三步全是它的使用方，先把契约立住，后面每一步都有一个固定的东西可以对着写。

2. **各使用方接上 URI。** 选目录器发出 URI 并可切设备，它不自己发现设备，设备清单由调用方注入。
   pi-web 服务端接收 URI 但只认本机，遇到 `ssh://` 直接拒绝并给出明确错误，因为 pi 的会话目录都在工作台所在机器上。它的选目录器不注入设备清单，远程目标不会到达它的服务端。
   ssh-web 加上 `ssh-args` 接口与按 cwd 开终端：终端接口接受 `cwd`，远端没有对应 tmux 会话时在初始目录新建会话，已有会话时在该目录新开一个 window 再 attach，终端标签携带这个远端初始目录。
   fs-web 加上 ssh provider，远程目录与本机共用同一套树、编辑器与目录操作。
   这一步里几个使用方互不依赖，可以并行做，做完各自带 URI 跑通自己的场景。

3. **组合根接线。** [registry.tsx](../../../apps/shell-web/src/registry.tsx) 先建 ssh，再把它的 `listDevices` 与 `openTerminal` 注入给 fs-web 的 `host` 选项，fs-web 的目录右键对 ssh 位置显示「在此打开终端」。
   这条边登记在注册表页的 `WIRES`，在页面上直接看得见。fs-web 不 import ssh-web，只接两个函数，ssh 被移除时这里直接编译失败。
   放在第三步是因为它需要前两步的两端都已就位，而且它是唯一同时看见两个模块的地方，不适合与功能开发混在一起。

4. **文档。** 各模块的 `SPEC.md` 与 `README.md` 同步到新形态，本设计在 `ARCHITECHTURE.md` 的设计索引里登记，让后来的人能顺着索引找到这些取舍。

四步的顺序也是风险的顺序。
第一步是纯函数，有测试向量兜底。
第二步每个使用方各自验证，出错的影响不出模块。
第三步是接线，两端都已就位，接错了在编译期就暴露。
到最后一步才动文档，此时形态已经稳定，写下来的就是实际落地的样子。

## 明确不做的

- 没有 Project 实体。项目是 todo-web 与 flow-web 各自的概念，两边对项目的定义并不相同，基座不替它们定一个共同的，也就避开了「谁的项目才是真的」这个争论。
- 没有基座服务。多一个有状态的进程只多一个要备份、要迁移、要排障的东西，而问题只是缺一个说法。
- todo-web 与 flow-web 不改。它们传给 fs-web 的裸路径由 fs-web 侧包成 `file://`，效果与传 URI 相同，改了也只是把同一件事换个写法，不带来新能力。等它们真要打开远程目录时再改，那时改的是发送方而不是契约。
- ssh 目录上的 git 返回 501。在远端跑 git 意味着一次操作要拉回整份状态输出，解析还要在本地重做一遍，先留给终端里直接敲。
- 不做跨主机复制。它需要两边同时在线并协调传输，出错的方式与单机完全不同，和「标清一个位置」不是同一个问题。
- 不做远程 watch。远端没有可靠的 inotify 桥，轮询的开销与收益不相称，先用刷新按钮。
