# 执行器管理平台拆分提案

Workbench 和 Flow Runtime 连接同一个执行器管理平台。平台发布执行器，调用方传递固定版本的 `executorRef: {id, revision}`。同一引用在两个产品中指向同一份配置快照和后端绑定。平台地址和访问权限由部署者分别配置，引用本身不授予执行权。

## 三方各管什么

| 模块 | 拥有的数据和操作 | 用户入口 |
| --- | --- | --- |
| 执行器管理平台 | 后端登记、检查和授权，执行器定义、定制、试跑、发布与停用，配置包及目录约束，配置快照，执行尝试和只读制品 | 独立管理页负责编辑、试跑、发布和检查后端。Workbench 可从导航打开同一页面 |
| Workbench | 工作清单、工作包、业务输入及生成来源；保存所选执行器引用和尝试 ID | 工作包页选版本并直接执行，或选 Flow 和执行器后启动整条流程，展示状态与制品 |
| Flow Runtime | Flow 包和修订、节点指令、节点执行记录、变量校验、路由、停止与恢复 | 独立启动和嵌入 Workbench 使用同一运行契约。命令节点、子 Flow 和图控制仍由 Runtime 调度 |

从 Workbench 迁出 `agent_backends`、`catalog` 中的执行器发布与资源解析、`patches` 中的配置包、`executor` 的尝试管理以及对应管理页面。配置包编辑器继续维护 `AGENTS.md`、`skills/` 和 `mcp.json`。试跑只冻结本次草稿；发布时固定快照和后端，后续改包不影响旧修订。业务工作包与生成器留在 Workbench。两个产品可复用目录编辑组件，各自管理自己的文件，不共同写 `work.json`。共享的资源定义应保留一个发布方，另一方按版本引用。

## 一次运行怎样传递

以“审核”节点为例。Workbench 在平台选中 `reviewer@7`。直接执行工作包时，Workbench 把 `{id: "reviewer", revision: 7}`、指令和输入交给平台。启动 Flow 时，Workbench 通过现有 Flow 客户端把同一引用交给 Runtime；独立控制台也可以提交相同的启动参数。首版一个 Run 指定一个执行器，供其中委派的 Agent 节点使用。启动前校验版本、权限与节点能力，Runtime 将引用与 Flow 修订一同保存。

1. Runtime 进入“审核”时，先持久化本次节点执行与新 `attemptId` 的对应关系，再调用平台。循环再次进入同一节点时分配新 ID；同一次请求丢失回执时使用原 ID 查回。Run 的 ID、节点名和尝试 ID 各有用途。
2. 平台按引用取冻结快照，为本次尝试准备输入和工作区，经[既有 MCP 协议](../../EXECUTOR-MCP.md)启动绑定的后端。消费者走服务 API，MCP 是平台与后端之间的协议，两侧各自独立。不把配置包、可执行路径、密钥或 MCP 连接随 Flow 传递。
3. 平台负责按 `attemptId` 查询、取消、收集制品。Runtime 停止 Run 时取消其活跃尝试，恢复时查询原尝试。`unverified` 表示待核实，不触发路由或自动换后端重跑。Workbench 独立执行工作包时使用相同语义。
4. 对 Flow 节点，适配器须支持[节点结果契约](../../../flow-runtime/docs/flow-spec.md)：接收本次可选结果与变量声明，向会话提供 `submit_flow_outcome`，将提交的结构化结果保存为该尝试的结果制品。平台把制品交回 Runtime，Runtime 校验后才按“通过”或“退回”等结果选边。仅有 MCP `succeeded`、结果缺失或非法，都不能推进节点。现有 Pi 适配器只接受空 `runConfig`，接入前须实现并声明此能力，普通工作包执行器不必支持它。

## 文件和权限边界

平台接受调用方提交的、已获准的输入文件快照，不读取 Workbench 的 `workPatchId` 或 Runtime 的任意宿主路径。两者分别从工作包或节点所需材料生成快照，平台按尝试保存并将只读制品提供给原调用方。需要把前一节点的产物用于下一节点时，由 Runtime 显式选择并传入。首版委派只适用于显式输入和产物的节点；依赖原地修改 Run 工作目录的节点，须先定义写回与冲突规则再迁移。

现有 `workspace:<attemptId>`、`artifacts:<attemptId>` 只是在同一私有根目录下定位文件。首版将平台与 stdio 后端部署在同一文件系统，Workbench 和 Runtime 可作为独立客户端。异机后端须具备按尝试授权的材料下载和产物上传，且平台确认收齐后才能对调用方发布结果。管理权限与启动、查询本次执行的权限分开，客户端只取得所需权限。

## 迁移与验收

1. 先抽出平台服务、独立存储和管理页，接通 Workbench 的工作包直跑。切换时保留配置包 ID、执行器 ID、修订及冻结快照，核对原有引用后切换唯一写入口。验收：同一草稿可试跑再发布，发布后修改配置包，旧版本仍按发布时的配置执行。
2. 扩展 Flow 启动契约，接通一个支持结构化结果的 Agent 节点。用同一版本从独立 Runtime 和 Workbench 分别启动 Flow，核对节点输入中的唯一标记、输出制品和实际分支。关闭 Workbench 后独立运行仍可完成。仅启动平台时也可直接执行工作包材料，无需启动 Runtime。
3. 在启动回执丢失、Runtime 重启和取消场景下核实同一节点只执行一次；确认非法结果不会选边、跨调用方无法读取尝试。已有“整条 Flow 作为 MCP 执行器”的适配器与这里的节点执行器分开登记，不作为节点委派目标，以免形成递归调用。
